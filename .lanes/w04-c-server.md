## Decisions
- **R15/R16 rules are parameters** (`R15Rules`/`R16Rules`: allowlist, native coin, Solana limits and `sameAddress`/`parseAtomic`), so core has no runtime import and not even a type import of `@hako/*` (the plugin typechecks it on a clean clone without the root install). `r15RulesFor`/`r16RulesFor` in `./server` show the assembly; the plugin (L1) builds the same object from its relative imports of config/networks/money.
- **R15 binds more than the plan's list, all fail closed**: to-chain and to-token too, the EVM tx's `chainId` and `from`, and `value` (an ERC-20 move must send 0 native; a native move exactly the amount). A route that charges a native fee on an ERC-20 transfer is therefore refused — the route race should run `bindQuote` at quote time to drop such rows. Solana also refuses non-canonical base64 and versions other than legacy/v0.
- **`NormalizedQuote` satisfies `DraftQuote`** (checked at compile time in `@hako/paybox/src/contract-checks.ts`); its `expiresAt` = `quotedAt + QUOTE_CACHE_TTL_S`; `approvalAddress` is null for native coins and Solana.
- **drafts table = versions table**: the PK `(draft_id, version)` is the unique row; `claimDraftExecution` sets `executed_at` once (the "insert the unique row first" step), `recordDraftRequest` sets the request id once. DraftStore maps 1:1: insertDraft→`insertDraft`, getDraft→`getLatestDraft`, getVersion→`getDraftVersion`, appendVersion→`appendDraftVersion`, setState→`setDraftState`, claimExecution→`claimDraftExecution`, recordRequest→`recordDraftRequest`, getExecution→`getDraftExecution` (rows carry `Date`s; the adapter turns them into ISO strings).
- **One active PayBox link per user** (partial unique index); revoked links stay as history. Disconnect only clears tokens (plan §1: every reconnect reuses the client). A new client is registered only after a revocation: `invalid_client`/`invalid_grant` on refresh, `invalid_client` at the code exchange, a changed `PAYBOX_OAUTH_REDIRECT_URL` (PayBox matches redirects exactly), or `begin(userId, { newClient: true })`. `sub` is an attribute set once; a different `sub` on the same client throws `PayboxSubjectMismatchError` (L4 picks the UX; SP10 still pending).
- **Better Auth Phase 1 enables no sign-in method** (only what the brief lists: sessions, `jwt()`, `nextCookies()`); how a Hako user is created (e.g. the anonymous plugin + Connect PayBox) is L4/L5's call, with a new migration from `migration:generate` if it adds columns.
- **`@hako/db/migrate` is its own entry**: Turbopack resolves `new URL('../migrations/', import.meta.url)` as an asset, so the runner stays out of the root and `/node`.
- **`@hako/defi/server` has no `server-only` guard**: gateway and CLI only (ESLint already bans it in client code). Next code doesn't import it (the web reaches LI.FI through the gateway).
- **Dependencies outside the catalog**: `@types/pg` 8.23.1 (the types of the §3 `pg` pin, published 2026-08-17) in db; `tsx` 4.23.15 (the version the lockfile already had for the gateway) as defi's test runner — `@hako/money`'s parameter properties stop Node's own type stripping. `erasableSyntaxOnly` is on in db and auth so their Node-run scripts stay strippable.

### 1. `packages/paybox/src/paybox.config.ts:43` — duplicated `HEX_RADIX`

### 2. `packages/db/src/shared.ts:10` — third `AtomicString`
`@hako/db` no longer declares or exports `AtomicString`. `packages/db/package.json` gains `"@hako/defi": "workspace:*"` (lockfile updated), and `receipts.ts`/`invoices.ts` take `import type { AtomicString } from "@hako/defi/core"` (type-only, so nothing of defi runs in db and Node's type stripping still runs the migrate script). Not re-exported: nothing outside db needs it from `@hako/db`. The `@hako/paybox` intents copy (foundation's `intents/types.ts`) is outside this finding and left as is.

### 3. `packages/db/src/shared.ts:33` — keyset paging skipped rows; tx hash case made a second receipt
- `PageOptions.before` is now a `PageCursor` `{ createdAt: Date; id: string }` (the last row read satisfies it). All five list helpers (`listReceiptsForUser`, `listReceiptsForAddresses`, `listPublicReceipts`, `listInvoicesByPayTo`, `listInvoicesByCreator`) filter `($n::timestamptz is null or (created_at, id) < ($n::timestamptz, $n+1::text))`, with the parameters from one helper (`cursorParams`).
- The tuple alone is not enough: `created_at` was microsecond `timestamptz` and a JS `Date` keeps milliseconds, so the cursor read back from a row compares *below* its own row and every row in that millisecond is skipped (checked on Postgres 16: three rows from one transaction, a millisecond cursor from page 1 → page 2 returned 0 rows even with the tuple filter). New migration `0003_keyset_paging.sql` stores `created_at` as `timestamptz(3)` on receipts and invoices (lossless for a `Date`), and rebuilds the list indexes as `(…, created_at desc, id desc)`. 0002 is untouched (never edit an applied migration).
- Tx hashes: `recordReceipt`, `findReceiptByTx` and `updateReceipt` store/look up EVM hashes (chain `eip155:*`) lowercase; `destTxHash` follows `toChain` (else `chain`). Solana signatures are base58, where case matters, and stay as given. `updateReceipt` does it in SQL against the row's own chain (`starts_with(chain, $8)`). 0003 adds `NOT VALID` check constraints (`receipts_evm_tx_hash_lowercase`, `receipts_evm_dest_tx_hash_lowercase`) so any other writer (the gateway) cannot store a mixed-case EVM hash and split the `(kind, chain, tx_hash)` unique index.
- Verified on a throwaway Postgres 16 (scratch script, not committed): `migrate` → 3 applied, re-run → 0 applied / 3 skipped; 3 receipts in one `withTransaction` share `created_at`, and paging each of the three receipt lists and both invoice lists with `limit: 1` returns every row exactly once; `0xabc0` then `0xABC0` → one receipt (`created: false`, same id), `findReceiptByTx(… "0xAbC0")` finds it; Solana `5abCD`/`5ABcd` stay two; `updateReceipt` lowercases an EVM destination hash on a Solana→Base move and an EVM source hash on a Base→Solana move while keeping the Solana one; a raw mixed-case EVM insert is refused by the check.

### 4. `packages/paybox/src/mcp.ts:141` — `client()` closed itself under its caller
`client()` is gone. `PayboxMcpSession` now has `acquire(): Promise<PayboxMcpLease>` (`{ client, release }`: increments the hold count and clears the idle timer; `release()` is idempotent and re-arms the timer only when the count reaches 0) and `withClient(work)` (acquire → work → release). The idle timer re-checks the count before closing, so it never closes while a lease is held. `close()` still closes at once. Verified with a scratch in-process MCP responder (idle 50 ms): a held lease's `client.tools()` works after 4× the idle window and after a concurrent `call()`; after release the client closes ("closed client"), and `withClient` reconnects (second `initialize`).

### 5. `packages/paybox/src/token-store.ts:131` — Disconnect revoked the client
- New `clearPayboxTokens(q, linkId)` in `@hako/db`: nulls `access_token_enc`, `refresh_token_enc`, `access_expires_at`, keeps `revoked_at` null, `client_id` and `sub`; true when there were tokens to drop. `disconnect(userId)` (token store and `PayboxServer`; the unused `reason` parameter is gone) uses it, so `connect.begin` → `clientFor` returns the same link and the same `client_id`, and earlier requests stay readable.
- `revokePayboxLink` stays for `invalid_client`/`invalid_grant` on refresh (PayBox: a replayed refresh token revokes the client) and the changed redirect URL. An expired access token with no refresh token now clears tokens instead (the client is still valid; only a new authorization is needed).
- Because the client now outlives a Disconnect, two recovery paths keep a user from being stuck on a client PayBox no longer accepts (its Clients screen revokes clients, and the Disconnect copy sends users there): `finish` revokes the link when the code exchange answers `invalid_client` and throws `PayboxConnectStateError` ("Start Connect PayBox again" → the next `begin` registers a new client); `begin(userId, { newClient: true })` revokes and registers up front (for L4's "start over" or "use a different PayBox account" after `PayboxSubjectMismatchError`, since a reused client keeps its `sub`).
- Verified against throwaway Postgres + Redis with PayBox's OAuth endpoints answered through the `fetch` hook: connect → disconnect (`access` → `PayboxNotConnectedError`) → `begin` returns `client-1` again with no second registration → `finish` stores tokens on `client-1`; an `invalid_client` exchange revokes it and the next `begin` registers `client-2`; `begin({ newClient: true })` revokes `client-2` and registers `client-3`.
